# Overlay Box Expansion by OCR Engine Plan

1. **概要（1–3行）**
- WinRTとPaddle OCRで検出枠の特性が異なるため、オーバーレイ拡張はWinRTのみ適用する。
- Paddle OCRは生の検出枠をそのまま描画し、過剰な拡張を避ける。

2. **ゴール / 非ゴール**
- ゴール: WinRTは従来通り枠拡張、Paddle OCRは拡張しない。
- ゴール: 同一画像での枠過大表示を抑えて可読性を上げる。
- 非ゴール: OCRモデルや検出精度の変更。
- 非ゴール: 既存のOCR前処理/後処理の調整。

3. **前提・仮定**
- オーバーレイ描画は現行のOverlayPresenter/描画パイプラインで行われる。
- 拡張量は現在の設定/既存ロジックを維持する。

4. **現状整理**
- オーバーレイ枠拡張はOCRエンジンに関係なく一律適用されている。
- Paddle OCRは検出枠が大きめで、拡張すると過剰になる。

5. **提案アーキテクチャ**

   * コンポーネント構成
   - Overlay描画部（OverlayPresenter または関連サービス）にエンジン別分岐を追加。

   * データフロー / シーケンス（文章で可）
   - OCR結果生成 → 描画前に「拡張可否」を判断
   - WinRT: 拡張適用
   - Paddle OCR: 拡張無効（raw box）

   * 既存パターンへの整合
   - 拡張ロジックは現状のまま再利用し、適用条件のみ切替。

6. **インターフェース設計**

   * API / 関数 / イベント / Queue / DB スキーマ変更
   - Overlay描画関数にOCRエンジン種別を渡す（既にSettings参照ならそのまま分岐）。

   * 入出力、エラー、バリデーション
   - OCRエンジンがPaddleのとき拡張パラメータを無視。

7. **実装手順（ステップ分割）**

   * Step 1…
   - 拡張処理の呼び出し位置を特定（OverlayPresenterなど）。

   * Step 2…
   - settings.OcrEngine == Paddle の場合は拡張をスキップ。

   * Step 3…
   - 描画結果を確認し、WinRTは従来通り拡張されることを確認。

8. **非機能要件チェック**

   * 性能: 分岐追加のみで性能影響は軽微。
   * 可観測性: 変更ログは不要。
   * 互換性: UI設定は変更しない。

9. **リスクと緩和策**
- Risk: Paddle OCRの枠が小さすぎるケースで可読性が下がる。
- Mitigation: 必要ならPaddle専用の軽量拡張率を別途導入。

10. **影響範囲**
- 変更ファイル候補
  - Services/OverlayPresenter.cs（または描画処理ファイル）
- 移行: なし
- ドキュメント更新: 本ファイル

11. **Definition of Done**
- WinRTは従来通り枠拡張される
- Paddle OCRは枠拡張されない
- 同一画像でPaddle OCRの枠が過剰に広がらない
