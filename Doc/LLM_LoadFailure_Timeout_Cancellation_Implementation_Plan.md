# LLM 読み込み失敗・タイムアウト・キャンセル対応 修正案

作成日: 2026-10-08  
対象: 翻訳用 Llama.cpp と VisionLLM OCR の読み込み処理  
状態: 実装済み。自動回帰テストと実モデルの CPU 起動・破損モデルによる失敗検知を確認済み。WPF ダイアログの目視確認は未実施。

## 1. 概要

LLM の起動失敗を速やかに検知し、読み込み表示を終了してから原因を表示する。
環境準備・モデル取得・モデル読み込みを区別し、通信待機と準備処理に時間制限を設ける。
読み込み中のキャンセルを末端の処理まで伝え、失敗・時間切れ・ユーザー中断を区別する。

## 2. ゴール / 非ゴール

### ゴール

- Python ホストや llama-server の起動失敗を、通常の準備完了タイムアウトまで待たずに検知する。
- 準備確認の通信が応答しなくても、既存の準備完了待機時間を超えて待ち続けない。
- 失敗時は読み込み表示とキャンセル操作を終了し、対象モデル・工程・原因を表示する。
- 長時間処理の工程が分かり、キャンセル後に操作可能な状態へ戻る。
- 初回起動・設定保存・手動再起動のすべてで同じ終了規則を使う。

### 非ゴール

- 翻訳・OCR の推論中のエラー処理全体を作り直すこと。
- 新しい OCR/翻訳エンジンへのフォールバックや自動リトライを追加すること。
- モデルの自動選択、分割ダウンロード、途中再開、ダウンロード管理画面の追加。
- 全 gRPC ホストの動作を一律に変更すること。共通部を変更する場合も今回の主対象は Llama/VisionLLM とする。
- llama.cpp の通常ログに含まれる単語だけで失敗を判定すること。
- 起動成功後の自動再起動方針の全面変更。

## 3. 前提・仮定

- Llama と VisionLLM は C# → Python gRPC ホスト → llama-server の構成である。
- 両 Python ホストは llama-server の準備完了を待ってから gRPC サーバを開始する。通常の初回読み込み中には Health API 自体へ接続できない。
- Python の `_wait_ready()` は llama-server の終了を確認し、失敗時には例外を発生させる。初回起動の失敗は `server.py` を通じて Python ホストの終了へ伝わる。
- C# の待機上限は通常 Llama 60 秒、VisionLLM 120 秒。既存の設定値をモデル読み込み工程の上限として使う。
- 初回準備・低速回線・大容量モデルを正常に処理する必要がある。モデル読み込みの上限をそのままダウンロードへ流用しない。
- 下記の準備・通信の時間制限値は提案値。実装時の検証で調整し、値と変更理由をコメントに残す。
- 作業開始時点で `Hotkey-Translator.csproj` に既存の未コミット変更がある。本計画作成では変更しない。

## 4. 現状整理

| 関連箇所 | 現行挙動と問題 |
| --- | --- |
| `Services/LlamaGrpcHost.cs` | `WaitForReadyCoreAsync()` に Python ホスト終了の確認がない。Health の例外を一律に握りつぶす。 |
| `Services/VisionLlmGrpcHost.cs` | Python ホスト終了の検知はあるが、Health 通信の待機を個別に制限していない。 |
| 両ホストの Health 呼び出し | RPC の deadline が未指定。ループ入口の時間判定だけでは、応答しない RPC の待機を打ち切れない。 |
| `Services/GrpcHost/GrpcHostOrchestrator.cs` | `catch` 内でエラーダイアログを出し、その後の `finally` で読み込み表示を解除する。キャンセルも一般エラーとして処理する。 |
| `Services/Application/ResourceHostFacade.cs` | `EnsureResourceHostsAsync()` が `CancellationToken.None` を渡す。読み込み gate の待機もキャンセルできない。 |
| 両ホストの `EnsurePythonRuntimeAsync()` | `uv sync` の終了待機に工程固有の時間制限がない。トークンは受け取るが、現在の UI 経路からユーザー中断を伝えられない。 |
| `Services/ModelAssetProvisioner.cs` | HTTP の時間制限が無限。既存の lock 待機は最大 10 分。ファイルの SHA-256 検証は同期処理で中断できない。 |
| `Services/Application/ResourceHostCommandController.cs` | 再起動操作にも独自の busy 表示と通知があり、読み込み側と責任が重複する。失敗しても戻り値によっては成功ログを出し得る。 |
| `MainWindow.xaml` / `MainWindow.xaml.cs` | キャンセルボタンは OCR/翻訳実行用の `CancelCurrentRunCommand` に接続されている。リソース読み込みへ接続されていない。 |
| `Services/Application/BusyOverlayController.cs` | 進捗スコープは直前の busy 状態を復元する。外側の「再起動中」表示を残したまま内側だけ終了すると、表示が復活し得る。 |
| `Services/Application/SettingsUiController.cs` / `OnLoaded()` | 読み込みの戻り値は「設定が変わったか」の bool。読み込み成功・失敗・キャンセルを表現できない。 |

### 既存の失敗時設定変更

- Llama は `EnableLlamaCppTranslation = false` に戻す。
- VisionLLM は `OcrEngine = WinRt` に変更する。既存メッセージの「OFF に戻した」は実態と一致していない。
- 本案ではこの既存動作を維持し、表示文言を実際の変更に合わせる。新しいフォールバックは追加しない。
- ユーザーキャンセルを失敗扱いして、上記の設定変更を実行することは避ける。

## 5. 提案アーキテクチャ

### 5.1 読み込み操作の責任を一本化する

- `ResourceHostFacade` がリソース読み込み操作の gate・CTS・操作識別子を所有する。
- `GrpcHostOrchestrator` は各ホストの開始、失敗情報の収集、現在の失敗時設定変更を担当する。UI ダイアログは直接出さない。
- 読み込み表示の開始・進捗・終了は一つの UI 操作スコープから行う。手動再起動の外側に別の busy 表示を残さない。
- gate を取得してから操作を開始し、取得していない要求が現在の表示や CTS を上書きしないようにする。
- 対象ホスト・モデル・工程は開始時の設定から確定する。処理中の UI 編集で対象名が変わらないようにする。
- 一度終了した操作の遅延進捗は操作識別子で破棄する。進捗コールバックが busy 表示を再び ON にすることを防ぐ。

### 5.2 明確な起動失敗を即時に検知する

- Llama の待機にも `TryGetProcessExitCode()` を使う。検査は通信例外の再試行用 `catch` の外で行う。
- 準備確認 RPC を待っている間も Python ホストの終了を監視し、終了したら RPC をキャンセルして起動失敗とする。
- Python 側は既存の llama-server 終了検知を維持する。終了コードを例外に含め、初回起動失敗時には残存する llama-server を停止する。
- C# 側で読み込み失敗・時間切れ・キャンセルが確定したら、当該ホストと追跡済み子プロセスの停止を完了する。
- 起動成功前は自動再起動監視を開始しない。既存の `StartAsync()` の順序を維持する。
- stderr の末尾をホストごとに最大 50 行・16 KiB の範囲で保持し、終了コードだけでは分からない原因の補助情報にする。過去の読み込みの内容は開始時に破棄する。
- stderr に `error` があるだけでは失敗扱いしない。終了、RPC の明確な異常、検証例外、時間切れを根拠とする。

### 5.3 時間制限を工程ごとに設ける

| 処理 | 提案する上限 | 期限到達時 |
| --- | --- | --- |
| 環境準備 (`uv sync`) | 工程全体 15 分 | uv のプロセスツリーを停止し、環境準備の時間切れを通知 |
| モデル取得の応答ヘッダー待ち | 15 秒 | 接続・応答待ちの時間切れとして終了 |
| モデル取得のデータ受信 | 連続 60 秒受信なし、かつ asset ごとに全体 60 分 | 取得を中止し、当該操作の未完成ファイルを削除 |
| モデル取得の lock 待機 | 既存の 10 分 | 他処理による使用中として明示通知。ユーザーキャンセルは即伝播 |
| モデル読み込み・gRPC 準備完了 | 既存 `LlamaGrpcReadyTimeoutMs` / `VisionLlmGrpcReadyTimeoutMs` | 読み込み時間切れとしてホストを停止 |
| Health RPC 1 回 | 最大 2 秒、残りの準備完了待機時間が短ければその残り時間 | 未接続・一時的応答なしは残り時間内のみ再確認 |

- 工程全体の期限は単調時間 (`Stopwatch`) で計測し、OS 時刻の変更に影響されないようにする。
- RPC の deadline に加え、全体期限・ユーザー中断・アプリ終了と連動した CTS を使用する。2 秒ごとの通信期限を全体の時間切れと区別する。
- `Unavailable` と通信単位の `DeadlineExceeded` は起動途中として待機を続けられる。その他の明確な RPC 異常を一律に握りつぶさない。
- 個別 RPC の時間切れ後も、全体期限を延長しない。全体期限を過ぎたら新しい RPC を発行しない。
- `GrpcStartupTimeoutPolicy` の初回 15 分扱いは、Llama/VisionLLM では環境準備工程へ分離する。準備後のモデル読み込みを不要に 15 分待たせない。他 OCR ホストの扱いは維持する。
- ダウンロードはストリーム読み込みごとに受信停滞を判定する。数 GB のファイルに対して単純な短い全体 HTTP timeout だけを適用しない。
- 既存ファイル・取得ファイルの SHA-256 検証もキャンセル可能な非同期読み込みにする。検証前後のキャンセル確認だけで大容量検証中を待たせない。

### 5.4 工程表示とキャンセル

| 工程 | 表示例 | 進捗 |
| --- | --- | --- |
| 環境準備 | `Llama.cpp: 実行環境を準備中…` | 不定表示 |
| ロック待機 | `Llama.cpp: モデルを使用中の処理を待機中…` | 不定表示 |
| モデル取得 | `Llama.cpp: xxx.gguf をダウンロード中…` | 合計サイズが分かる場合のみ bytes に基づく割合 |
| ファイル検証 | `VisionLLM: モデルファイルを検証中…` | 不定表示 |
| モデル読み込み | `VisionLLM: xxx.gguf を読み込み中…` | 不定表示 |
| gRPC 接続確認 | `VisionLLM: 接続を確認中…` | 不定表示 |
| 中断処理 | `読み込みを中止しています…` | 不定表示、キャンセルボタンは無効化 |

- Python が既に出力している準備完了の情報を工程表示へ使う場合は、両 Python ホストに固定の構造化された工程通知を加える。任意のログ文言に依存しない。
- 工程通知は UI のための情報に限定する。起動成功の最終判定は Health の `Ready = true` とする。
- 通知の解析失敗は起動失敗の原因にしない。工程は最後に確定した表示を保ち、Health 判定を継続する。
- 既存の busy 表示を使うが、キャンセル対象を「現在のリソース読み込み」と「OCR/翻訳実行」で明確に分ける。
- UI の共通キャンセル入口は、読み込み操作があれば読み込み CTS をキャンセルし、それ以外では既存の `CancelCurrentRun()` に送る。
- 初回 `OnLoaded()` の途中でもキャンセルを受け付ける。まだ作成されていない run coordinator を前提にしない。
- キャンセル後は停止・ファイル後始末を完了してから busy 表示を閉じる。連打による追加要求を受け付けない。
- 進捗更新は最大 4 回/秒程度に制限し、終了後に UI へ届いた通知は破棄する。

### 5.5 終了シーケンス

1. 成功、失敗、時間切れ、ユーザーキャンセル、アプリ終了を区別して確定する。
2. 失敗・中断した当該ホストと準備用プロセスを停止し、未完成ファイルを後始末する。
3. 操作を終了済みにし、進捗通知・キャンセル受付を止める。
4. UI スレッドで読み込み表示を解除する。
5. 操作 CTS と gate を解放し、結果を呼び出し元へ返す。
6. 失敗・時間切れの場合だけ、呼び出し元が一度エラーダイアログを表示する。ユーザーキャンセルは中断ログのみとする。

全体の `finally` は UI と gate の解除を保証する。ただし、失敗通知はその終了処理後に行う。
成功済みの別ホストを巻き戻すことはしない。ユーザーキャンセルは残りのホスト起動も中止する。
既存の失敗時設定変更は保ち、独立した別ホストを読み込む現在の挙動を維持する場合も、失敗結果を集約して一度だけ通知する。

## 6. インターフェース設計

### 6.1 操作結果と進捗

- `ResourceHostLoadResult`（仮称）: `Succeeded / Failed / Cancelled`、`SettingsChanged`、失敗情報のリスト。
- `HostLoadFailure`（仮称）: host ID、モデル名、mmproj 名、工程、理由区分、例外メッセージ、終了コード、制限済みの診断情報。
- `HostLoadProgress`（仮称）: 操作識別子、host ID、工程、asset 名、受信 bytes、合計 bytes。
- 理由区分は `ProcessExited / Timeout / ValidationFailed / PreparationFailed / CommunicationFailed` 程度とし、ユーザーキャンセルを含めない。
- 型は必要な情報を受け渡す内部 DTO に留め、汎用ワークフロー基盤を追加しない。

### 6.2 関数・イベントの変更案

- `ResourceHostFacade.EnsureResourceHostsAsync()` を操作結果を返す形へ変更し、呼び出し元の cancellation token を受け取る。gate の取得にも同じ token を渡す。
- facade に現在の読み込みを中断する入口を設ける。アプリ終了時も同じ CTS に中断を伝える。
- `GrpcHostOrchestrator.EnsureHostsAsync()` は結果・失敗情報を返し、一般例外より先にユーザー中断を扱う。
- `GrpcHostDescriptor` はホストの進捗を接続するために必要な最小限の内部 I/F を持つ。共有 I/F を変更する場合は Paddle/PaddleVL/NDL の呼び出しも同時に更新する。
- `GrpcHostBase` は Llama/VisionLLM の起動診断情報を保持し、停止で失われる前に失敗情報へ取り込む。モデル名や工程は内部型で伝える。
- `LlamaGrpcHost` / `VisionLlmGrpcHost` は工程切替、時間制限、子プロセス終了を報告する。
- `ModelAssetProvisioner.EnsureAssetAsync()` に bytes 進捗通知と時間制限を渡す。既存の manifest・SHA-256・排他・検証後配置を維持する。
- settings bridge、`OnLoaded()`、設定保存、手動再起動の呼び出し元を bool の成功判定から操作結果の判定へ更新する。
- DB、gRPC proto、保存済み設定形式は変更しない。新しい時間制限の UI 設定は初期実装では追加しない。

### 6.3 エラー表示

例:

```text
VisionLLM の読み込みに失敗しました。
モデル: <選択した GGUF ファイル名>
補助モデル: <選択した mmproj ファイル名>
工程: モデル読み込み
原因: llama-server が起動中に終了しました（終了コード: …）。
詳細: <取得できた原因情報>
設定: OCR エンジンを WinRT に戻しました。
```

- 日英の resx キーで表示を組み立てる。対象と工程はコード側の確定情報を使う。
- モデル破損、モデル/mmproj 不整合、GPU メモリ不足などは診断情報に根拠がある場合のみ表示する。終了コードだけから原因を推測しない。
- 詳細が取れなければ終了コードまたは期限・例外情報を表示し、「原因の詳細はログを確認してください」と案内する。
- stdout/stderr 全文や接続 URL を無条件にダイアログへ貼らない。秘密情報を除外し、必要な範囲に制限する。

### 6.4 キャンセル時の設定・呼び出し元契約

- `Cancelled` では `DisableOnFailure()` を呼ばない。モデル選択を保持し、エラーダイアログを出さない。
- 実際に開始して未完了の対象だけを停止し、既に起動済みのホストは維持する。
- 未読み込みの選択済みホストはランタイム状態で識別し、自動翻訳から使われる際は「モデルが読み込まれていない」と明示して当該処理を止める。今回の操作をサイレントに再開しない。
- 同じアプリ実行中は、キャンセル済み対象を無関係な設定保存で自動再読み込みしない。明示的な再起動、対象の再選択・再有効化、次回アプリ起動で新しい読み込みを開始できる。
- この抑止は実行時のみとし、保存設定へ新しいキャンセル状態を追加しない。
- 設定保存でユーザーが選んだ設定は保存できるが、ログは「設定保存済み・モデル読み込みは中断」とする。手動再起動は `Succeeded` の場合だけ「再起動完了」を出す。
- 初回起動がキャンセルされた場合もメインウィンドウの初期化は続行し、未読み込み状態を表示する。
- アプリ終了ではダイアログを出さない。読み込み task の終了を待ってから gate とホストを破棄し、`finally` が破棄済み gate に触れないようにする。

## 7. 実装手順

### Step 1: 準備完了待機の失敗検知と期限を修正

- Llama のプロセス終了検知、両ホストの RPC deadline、全体期限と連動したキャンセルを追加する。
- Python の終了コードと起動時後始末を整える。
- 模擬ホストで「即終了」「応答しない Health」「正常に遅れて準備完了」を確認する。

### Step 2: 失敗情報と通知順序を修正

- 結果型・失敗情報型を導入し、既存 bool の `SettingsChanged` の意味を保持する。
- orchestrator の直接ダイアログ表示を外し、読み込み終了後に通知する。
- 再起動操作側の重複 busy 表示・通知と、失敗時の成功ログを修正する。
- 日英の対象モデル・工程・原因・設定変更のメッセージを追加する。

### Step 3: 操作全体のキャンセルを接続

- facade に CTS と操作識別子を持たせ、UI のキャンセルとアプリ終了を接続する。
- `uv sync`、gate 待機、準備確認へ token を伝える。
- 結果の `Cancelled`、設定保存、未読み込み状態、同一実行中の自動再読み込み抑止を実装する。
- 初回起動と手動再起動でも、未初期化の UI 要素へ触れずに終了できることを確認する。

### Step 4: 工程別進捗と準備工程の期限を追加

- 環境準備、取得、検証、読み込み、接続確認を進捗通知へ接続する。
- ダウンロードの応答待ち・受信停滞・全体期限、非同期ファイル検証を追加する。
- ロック保持中の後始末、完了後の遅延進捗破棄を確認する。
- Python 工程通知を導入し、表示と Health による成功判定を分ける。

### Step 5: 統合検証と利用者向け説明

- 初回起動、設定保存、Llama/VisionLLM 手動再起動を横断して確認する。
- 共通ホスト処理の変更が影響する Paddle/PaddleVL/NDL の正常起動・既存の失敗通知を確認する。
- `Doc/UserGuide.md` にキャンセルとエラー後の再読み込み操作を追記する。
- 実装完了時に `.agent/changes.md` へ一タスク一エントリで追記する。

Feature flag は設けず、各 step がビルド可能な単位で進める。内部 I/F の変更と呼び出し元更新は同じ step で行う。

## 8. 非機能要件チェック

- 性能: 不定表示のまま推定割合を作らない。bytes 進捗は頻度制限し、診断情報は固定容量で保持する。
- UI 応答: 大容量ファイル検証とプロセス終了待機を UI スレッドで実行しない。同期 dispatcher 呼び出しと停止待機の相互待ちを避ける。
- セキュリティ: URL の認証情報、API キー、環境変数の内容を新しい通知や診断記録へ含めない。
- データ保護: lock を取得した処理だけが自身の `.tmp` を削除する。検証済みの最終ファイルや別操作の資産をキャンセルで消さない。
- 互換性: 既存のモデル名・manifest・設定形式・準備完了時間設定を維持する。新しい旧形式サポートやフォールバックは追加しない。
- 可観測性: `operation_id / host / model / phase / event / elapsed_ms / timeout_ms / exit_code / reason` を必要なログへ追加する。失敗とキャンセルを別イベントにする。
- 運用: エラー後は設定と対象ファイルを確認し、利用者の明示操作で再読み込みできる。自動再試行ループを作らない。
- コメント: deadline の二段構成、キャンセルと失敗の分離、終了後の進捗破棄、未完成ファイルの保護に Why/NOTE/SECURITY コメントを残す。

## 9. リスクと緩和策

| リスク | 緩和策 |
| --- | --- |
| 正常な大容量モデルを時間切れと誤判定 | 準備と読み込みの期限を分け、読み込みは既存設定を維持。遅れて正常に ready になるケースを検証 |
| キャンセルと成功がほぼ同時に発生 | 終了状態を一度だけ確定し、成功確定前は token を確認。終了後の進捗を破棄 |
| キャンセルを故障扱いして設定を書き換える | 外部 token の中断を先に処理し、工程期限の中断と区別。Cancelled では DisableOnFailure を呼ばない |
| busy 表示が復活する・残る | 外側の再起動表示を統合し、操作スコープの所有者を一つに限定 |
| Python/uv/llama-server が残存 | 工程ごとに所有プロセスを追跡し、終了時に停止。別操作のプロセスを止めない |
| ダウンロード中断で別処理のファイルを消す | lock 保持中だけ `.tmp` を扱い、検証済みファイルを保持 |
| アプリ終了後に gate 解放や通知が走る | 中断→task 終了→破棄の順序を守り、終了時通知を抑止 |
| 共通 I/F 変更で他 OCR が壊れる | 全実装と参照を追跡し、コンパイル・正常起動・既存失敗処理の回帰を確認 |

## 11. Definition of Done

- [ ] Python ホストの即時終了が Llama/VisionLLM ともに検知され、準備完了の上限まで待たない。
- [ ] 起動失敗の終了コード・対象モデル・工程を表示できる。詳細がない場合も原因を推測しない。
- [ ] 応答しない Health RPC を模擬しても、全体期限内に打ち切られる。短い RPC 期限を全体期限に誤変換しない。
- [ ] 正常に遅れて ready になるホストは、設定した待機時間内で成功する。
- [ ] エラーダイアログ表示時には busy 表示が終了しており、閉じた後も再表示されない。
- [ ] 環境準備、取得、検証、読み込み、接続確認の工程が UI から区別できる。
- [ ] uv 待機、lock 待機、受信停滞、ファイル検証、ready 待機の各工程をキャンセルできる。
- [ ] ユーザーキャンセルでは失敗ダイアログ・DisableOnFailure・成功ログが出ない。
- [ ] キャンセル後もモデル選択が保持され、未読み込み状態が明示される。無関係な保存による勝手な再開がない。
- [ ] 初回起動の中断後もアプリの初期化が完了し、明示的な再読み込みが成功する。
- [ ] アプリ終了・キャンセル連打・終了直前の遅延進捗を検証し、残存プロセスや破棄済みオブジェクトへのアクセスがない。
- [ ] ダウンロード中断時の `.tmp` 削除と、完成済み asset・別操作のファイルの保護を確認する。
- [ ] 模擬 HTTP/gRPC サーバと模擬プロセスで期限・失敗・キャンセルを再現し、大容量モデルの実ダウンロードに依存せず検証できる。
- [ ] 両 LLM の実モデルで正常起動と手動再起動を確認する。VisionLLM は対応モデル/mmproj の組を使う。
- [ ] 共通部に影響する他 OCR の回帰確認、日英 resx 解析、`dotnet build`、既存 Python テスト、`git diff --check` を実施する。
- [ ] コメント・利用者ガイド・実装の変更記録を更新する。

## Open Questions

- 準備 15 分、受信停滞 60 秒、asset 全体 60 分で、想定する初回セットアップと回線速度を扱えるか。模擬検証と実機確認で調整する。
- GPU/モデル読込失敗の診断メッセージは llama.cpp の出力に依存する。固定の原因分類へ変換できない場合は取得した根拠を制限して表示する。
- 自動再起動が起動成功後に失敗したケースの UI 通知は、初回読み込みの修正とは別途確認する。本案で全面的な再起動方針変更は行わない。
