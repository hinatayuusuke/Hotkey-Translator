# WPF Settings Console Modernization Recommendation

## 1. 概要
このアプリの主役は `MainWindow` ではなく、対象アプリ上に表示される翻訳オーバーレイである。
したがって `MainWindow` は「メイン操作画面」ではなく、オーバーレイの挙動、使用エンジン、運用時の確認項目を調整するための設定コンソールとして設計する。

UI モダン化の目的は、一般的なランチャー風の見た目に寄せることではない。
設定変更、テスト、状態確認を短時間で安全に行える構造へ整理し、そのうえで標準コントロールを壊さない範囲で Fluent / Modern WPF 系の見た目に寄せることを優先する。

## 2. ゴール / 非ゴール
### ゴール
- オーバーレイの表示挙動を、設定コンソールから迷わず調整できること
- OCR / Translation / Hook / Hotkey / Runtime 状態の責務が画面上で明確に分かれること
- 設定変更後に、Preview / Log / テスト操作で結果をすぐ検証できること
- 高密度な設定画面でも、項目の意味と影響範囲が読み取りやすいこと
- 標準コントロールの操作感を壊さずにモダンな見た目へ寄せられること

### 非ゴール
- `MainWindow` をランチャーやダッシュボードのような見せる画面にすること
- すべての設定を同一密度・同一重要度で並べること
- 既存レイアウトの見た目をそのまま維持すること
- 大量の独自 ControlTemplate を導入して見た目を作り込むこと

## 3. 前提・仮定
- ユーザーの主な操作は対象アプリ側で行われる
- `MainWindow` は常時注視される画面ではなく、セットアップ、調整、トラブル時確認のために開く画面である
- 設定項目は今後も増える可能性が高く、再配置しやすい情報構造が必要である
- OCR 前処理やエンジン切替は、見た目よりも検証のしやすさが重要である

## 4. 現状整理
### 現行 UI の性質
- 1 つの `MainWindow.xaml` に多数の設定が集約されている
- 項目は実装都合ベースで分割されており、利用者の判断単位と完全には一致していない
- Preview / Log はあるが、設定変更の検証ペインとしての位置づけがまだ弱い

### 現行 UI の課題
- `Home` が設定画面と診断画面の中間になっており、役割が曖昧
- `VisionLLM` や `PaddleOCR` などに、日常設定と詳細設定が混在している
- 各セクションでラベル幅、説明文位置、補助ボタン配置がばらついている
- 見た目を整える前に、設定責務での再編が必要な状態である

## 5. 提案アーキテクチャ
### 5.1 基本方針
- `MainWindow` は「設定スタジオ」ではなく「設定コンソール」として設計する
- 画面構成はワークフロー順ではなく、設定責務順で整理する
- 高密度なフォームを許容しつつ、セクション単位で視線誘導を明確にする
- 見た目のモダン化は、余白、階層、抑制色、状態表示の整理を優先する

### 5.2 推奨ナビゲーション構成
- `Overview`
- `Capture`
- `OCR`
- `Translation`
- `Overlay Behavior`
- `Hotkeys`
- `Runtime / Logs`
- `Advanced`

### 5.3 各セクションの役割
#### Overview
- 現在の capture mode
- 現在の OCR engine
- 現在の translation route
- 現在の source / target language
- source / target language の即時変更
- language swap
- オーバーレイ状態
- 主な hotkey 一覧
- `Run test`, `Select ROI`, `Open log` などの即時操作

#### Capture
- 取得対象、ROI、固定対象、取得方式
- 設定値そのものより、現在どの入力を監視するかを中心に整理する

#### OCR
- OCR 共通設定
- OCR 前処理
- OCR エンジン選択
- OCR エンジンの基本設定
- 詳細なエンジン調整項目は `Advanced` または折りたたみへ逃がす

#### Translation
- 翻訳エンジン選択
- 優先順位
- 言語設定の詳細
- ローカル翻訳系ランタイムの基本制御

#### Overlay Behavior
- オーバーレイの表示条件
- Auto Translate 条件
- Overlay readability 関連
- Scene change と自動制御

#### Hotkeys
- ホットキー一覧
- 入力経路
- 対象アプリ操作中に影響の大きいトグルを集約する

#### Runtime / Logs
- Preview
- Log
- 現在状態
- エラー時の判断に必要な情報

#### Advanced
- Hook の詳細設定
- エンジンごとの高度なパラメータ
- 通常運用では触らない項目

### 5.4 情報密度の考え方
- 一般向けカード UI ではなく、整理された高密度フォームを採用する
- セクション単位でのみ薄いグルーピングを付ける
- 項目ごとの装飾は増やしすぎない
- 長大な画面は許容するが、見出しと補助説明で読める状態を保つ

### 5.5 Overview に置くべき主要設定
- `Overview` には、現在の構成を誤認しやすく、かつ変更頻度の高い主要設定だけを置く
- 特に言語選択は、オーバーレイ結果へ直接影響し、テスト操作とも近いため `Overview` に含める
- ただし `Overview` に置くのは最小限の言語ペア操作に留める
- 翻訳エンジン優先順位、詳細ランタイム設定、詳細な言語関連オプションは `Translation` に残す

## 6. インターフェース設計
### 6.1 レイアウトルール
- ラベル列幅を統一する
- 入力欄直下に説明文を置く
- 補助ボタンは入力欄の右側へ揃える
- 再起動が必要な項目は、項目直下で明示する
- 危険な設定や検証向け設定は muted ではなく注意表示で区別する

### 6.2 Basic / Advanced 分離
- `VisionLLM`, `PaddleOCR`, `Llama.cpp`, `Hook` は `Basic` と `Advanced` を分ける
- 日常的に触る項目だけを最初に見せる
- 調整用途の数値パラメータは Expander または別セクションへ分離する

### 6.3 Preview / Log の扱い
- Preview / Log は補助 UI ではなく、設定変更の検証ペインとして扱う
- 開閉式の drawer でもよいが、存在感は弱めすぎない
- OCR 前処理プレビューは `OCR` 設定との因果が見える位置づけにする

## 7. 実装手順
### Step 1. 画面責務を再分類する
- 現行の `Home / Settings` 的な構造を、設定責務ベースへ再整理する
- `Overview` と各設定カテゴリの境界を先に定義する

### Step 2. `MainWindow.xaml` をページ単位に分割する
- まず見た目変更より、ページ単位の `UserControl` 分割を優先する
- `MainWindow` 自体はナビゲーションと共通ステータスだけを持つ

### Step 3. 共通フォーム部品を作る
- セクション見出し
- ラベル付き入力行
- 説明文
- 補助ボタン付き入力行
- Basic / Advanced の切替ブロック

### Step 4. `Overview` と `Runtime / Logs` を整える
- 常用設定ではなく、現状確認とテスト操作に特化させる
- Preview / Log を「検証のための場所」として再定義する

### Step 5. `OCR` と `Translation` を整理する
- 項目数が多く、設定コンソールとしての価値が高い領域を先に整理する
- 共通化しやすい入力パターンをここで固める

### Step 6. `Overlay Behavior`, `Hotkeys`, `Advanced` を整理する
- 頻度の低い設定は後段でよい
- 高度設定は通常設定から視覚的に分離する

### Step 7. 最後にテーマと見た目を整える
- 標準コントロールの自然な操作を優先する
- Fluent / ModernWpf 系のテーマ導入は、構造整理後に最小限で行う
- 独自テンプレートは必要最小限に留める

## 8. 非機能要件チェック
### 性能
- 画面分割後も設定反映や状態更新が重くならないこと

### セキュリティ
- API キーやパスなどの機微情報は視認性と誤操作防止を両立する

### 可観測性
- 失敗時に Preview / Log / 状態表示で判断できること

### 互換性
- 既存設定ファイルとの整合を保ちつつ UI 再編を行う

### 運用
- テスト操作、再起動要否、現在の有効構成が UI から読み取れること

## 9. リスクと緩和策
- Risk: カテゴリ再編で既存利用者の muscle memory が変わる
- Mitigation: `Overview` に現構成サマリと主要操作を残し、移行初期の迷いを減らす

- Risk: 詳細設定を隠しすぎると調整作業が増える
- Mitigation: `Advanced` へ完全移動せず、Basic の近くから Expander で到達可能にする

- Risk: 見た目だけ先に変えると保守性が改善しない
- Mitigation: 最初にページ分割と共通フォーム化を行い、その後でテーマを入れる

## 10. 影響範囲
- `MainWindow.xaml`
- `MainWindow.xaml.cs`
- `ViewModels/MainWindowViewModel.cs`
- `ViewModels/SettingsViewModel.cs`
- 新規 `UserControl` 群
- 共通スタイル用 ResourceDictionary

## 11. Definition of Done
- `MainWindow` が設定コンソールとして役割分離されている
- `Overview` が構成サマリとテスト操作に特化している
- `OCR` / `Translation` / `Overlay Behavior` / `Hotkeys` / `Runtime / Logs` / `Advanced` の責務が明確である
- 日常設定と詳細設定が視覚的に分離されている
- Preview / Log が設定変更の検証ペインとして機能している
- 標準コントロールの操作感を壊さずに、見た目が一貫している
