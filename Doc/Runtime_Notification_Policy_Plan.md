# Runtime Notification Policy Plan

1. **概要（1–3行）**
- 本計画は、アプリ実行中の通知を「何を、どこに、どの強さで出すか」に限定して整理する実装案である。
- Setup/インストーラー通知は対象外とし、ランタイム通知のみを扱う。
- 方針は「状態常駐は増やさない」「進行中表示は現仕様維持」「要点のみトースト」「停止級は強警告」に統一する。

2. **ゴール / 非ゴール**
### ゴール
- 実行中UI通知の優先度を統一し、過通知と見落としを同時に減らす。
- 既存スピナー挙動（OCR実行中 / 翻訳実行中）を維持しつつ、重要イベントだけを追加通知する。
- 停止級エラーは必ず「要操作」として明示し、ログだけで埋もれない設計にする。

### 非ゴール
- Setupウィザード/配布時の通知整理。
- ログの詳細フォーマット変更。
- OCR/翻訳アルゴリズムやフォールバック判定ロジックそのものの変更。

3. **前提・仮定**
- 既存で右下スピナー（実行中インジケータ）が導入済み。
- 既存でログウィンドウ/ステータスバーが利用可能。
- 実行中イベント（フォールバック、固定ロック/解除、重大失敗）は既存処理フローから検出可能。

4. **現状整理**
- 実行中の進行状態は主にスピナーとログで把握している。
- 重要イベント（フォールバック・復旧・固定ロック/解除）の通知基準が未整理で、表示有無が揺れやすい。
- 停止級エラーがログ中心だと見逃しやすく、ユーザーの復旧行動が遅れるリスクがある。

5. **提案アーキテクチャ**
### 5.1 通知カテゴリ定義（今回の方針）
- カテゴリ1（常駐状態表示）: **採用しない**
  - 例: `固定中/未固定` の常時表示は追加しない。
- カテゴリ2（進行中インジケータ）: **現仕様維持**
  - `OCR実行中`
  - `翻訳実行中`
- カテゴリ3（情報トースト）: **追加対象**
  - フォールバック発生（例: Paddle失敗 -> WinRT）
  - 一時失敗から復旧
  - 固定対象ロック / 解除
- カテゴリ4（強い警告・要操作）: **追加対象**
  - OCR/翻訳ともに利用不可
  - 必須依存欠落で処理停止
  - 連続失敗で自動処理停止

### 5.2 表示面の役割
- 右下スピナー: カテゴリ2のみ。
- 右下トースト: カテゴリ3のみ（短時間表示）。
- オーバーレイ要操作警告（モーダル非使用）: カテゴリ4のみ。
- ログ: すべての詳細（通知は要約のみ）。

6. **インターフェース設計**
### 6.1 通知イベント契約（案）
- `NotifyInfo(string code, string message)` -> カテゴリ3
- `NotifyActionRequired(string code, string message, string? actionHint)` -> カテゴリ4
- `SetRuntimeSpinnerState(bool ocrRunning, bool translationRunning)` -> カテゴリ2（既存維持）

### 6.2 コード体系（案）
- `runtime.fallback.*`（例: `runtime.fallback.paddle_to_winrt`）
- `runtime.recovery.*`
- `runtime.capture_lock.*`
- `runtime.blocker.*`（利用不可/依存欠落/連続失敗停止）

### 6.3 表示ルール
- カテゴリ3は同種連発を抑制（クールダウン導入）。
- カテゴリ4は同一原因の再表示を抑制しつつ、未解決中はUI上で認識可能にする。
- 追加通知（カテゴリ3/4）はすべてオーバーレイで表示し、モーダル通知は使用しない。
- 通知本文は短文、詳細はログ参照へ誘導する。

7. **実装手順（ステップ分割）**
- Step 1: 通知マップ定義
  - カテゴリ2/3/4に属するイベント一覧を定数化。
  - カテゴリ1（常駐状態）は追加しない方針を明文化。

- Step 2: 既存スピナー経路の固定
  - `OCR実行中` / `翻訳実行中` の既存制御を維持し、他イベントを混在させない。

- Step 3: カテゴリ3（情報トースト）追加
  - フォールバック発生、復旧、固定ロック/解除の通知発火点を接続。
  - 同種連投の抑制（クールダウン）を実装。

- Step 4: カテゴリ4（要操作警告）追加
  - 利用不可、依存欠落停止、連続失敗停止を要操作警告として表示。
  - 復旧導線（設定画面を開く/再試行）をメッセージへ付与。

- Step 5: 回帰確認
  - Run/ForceRunでスピナー仕様が変わっていないこと。
  - 追加通知がログと二重矛盾しないこと。

8. **非機能要件チェック**
- UX
  - 実行中通知を最小限に保ち、注意が必要な時だけ強く知らせる。
- 可観測性
  - 通知コードをログに残し、再現調査を容易にする。
- 互換性
  - 既存スピナー挙動（カテゴリ2）を維持する。
- 性能
  - 通知処理でOCR/翻訳パスをブロックしない。

9. **リスクと緩和策**
- Risk: トーストが多すぎて逆に読まれない。
- Mitigation: カテゴリ3は対象を3種に限定し、同種クールダウンを設ける。

- Risk: 重大警告が重複表示され、操作を阻害する。
- Mitigation: カテゴリ4は同一原因を集約し、未解決中の再発火を抑制する。

- Risk: ログと通知文言が不一致になり混乱する。
- Mitigation: 通知コードを共通化し、ログにも同コードを記録する。

10. **影響範囲（変更ファイル候補・移行・ドキュメント更新）**
- `UI/OverlayWindow.xaml(.cs)` — トースト/強警告の表示レイヤ調整（必要時）。
- `Services/OverlayPresenter.cs` — 通知種別に応じた表示API追加（必要時）。
- `MainWindow.xaml.cs` / `Services/Application/*` — 発火点接続（フォールバック/復旧/固定ロック/解除/停止級エラー）。
- `Doc/*` — 通知運用ルールの更新。

11. **Definition of Done**
- [ ] カテゴリ1（常駐状態表示）を追加していない。
- [ ] カテゴリ2（OCR実行中 / 翻訳実行中）の現仕様が維持されている。
- [ ] カテゴリ3として「フォールバック発生」「一時失敗から復旧」「固定対象ロック/解除」が表示される。
- [ ] カテゴリ4として「OCR/翻訳ともに利用不可」「必須依存欠落で処理停止」「連続失敗で自動処理停止」が要操作警告で表示される。
- [ ] 追加通知（カテゴリ3/4）がすべてオーバーレイ表示で統一され、モーダル通知を使用していない。
- [ ] 通知とログの内容が矛盾せず、調査可能なイベントコードが残る。
